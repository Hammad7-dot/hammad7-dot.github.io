Case 05 · Retrieval-augmented systems

Docket — AI Document Q&A RAG API

Stack: FastAPI, LangChain, pgvector, Postgres, Redis Role: Solo build See the repo →

The problem

Answering questions against a pile of documents usually means either reading them by hand or wiring up retrieval and generation yourself: chunking, embeddings, a vector store, and a model that actually cites what it read instead of guessing. I wanted a real, self-hosted RAG API — not a notebook demo — that could take documents in, index them properly, and answer questions against them through a clean HTTP interface.

What I did

Built Docket: a FastAPI backend that ingests documents, chunks and embeds them with LangChain, and stores the vectors in Postgres via pgvector, with Redis in front for caching. A static HTML frontend (also called Docket) gives it a usable interface for uploading documents and asking questions, rather than requiring API calls by hand. The backend and frontend are deployed separately by design: FastAPI/Postgres/Redis need a persistent server, so the backend targets Railway (specifically a pgvector-enabled Postgres template, not the plain one), while the static frontend deploys independently to Cloudflare Pages.

Real screen recording — Docket's auth flow, gating document Q&A behind a signed-in account.

Fixing it for real, not just building it once

Getting this to a state where it actually reproduces from a clean clone took seven rounds of real fixes: a validation error handler, embedding dimension mismatches between the model and the pgvector column, stale tests, an Ollama healthcheck that wasn't checking anything, a Python 3.13/numpy version pin that broke installs, and pushing document_service.py test coverage to 100%. The seventh fix — resizing embeddings back to 1024 dimensions once Cohere was settled on as the production embedding provider — is packaged as a migration, ready to apply once deployment starts.

How it's built, no mystery code

Upload flow: a document comes in through the FastAPI endpoint, gets chunked, embedded (Cohere in production), and the vectors land in a pgvector column on Postgres. Query flow: a question gets embedded the same way, pgvector does a similarity search to pull the relevant chunks, and LangChain assembles them into a prompt for the answer. Redis sits in front of repeat lookups so the same query isn't re-embedded and re-searched every time. The frontend talks to the backend over a plain API_BASE URL and CORS is scoped to whichever origin it's actually served from — no wildcard origins once it's live.

The honest gap

Working end-to-end in local/dev — sign-in, auth, and the document Q&A flow all run, as shown above. Not on a public URL yet: the migration for fix #7, the Railway deploy, and wiring API_BASE/CORS_ORIGINS to the live frontend host are still outstanding. This case study will get a live demo link the moment that ships — the write-up above is accurate to what's built and running today, not what's planned.
